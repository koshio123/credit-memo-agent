## 2026-09-30 架空の融資内規と与信メモのテンプレート

- **決定**: 内規は実在の金融機関のものを使わず、模擬文書 `policies/credit_policy.md` を自作した。メモの雛形は `templates/credit_memo.md`。
- **理由**: 実際の内規は入手できず、公開もできない。条文に番号を振り、出典（第○条）として引用できる形にした。財務比率の算式と境界値、算定不能の扱いを附則で明記したので、そのまま `compute_ratios` のテスト仕様になる。
- **仕様の要点**: システムは可否・推奨を出さない（第3条）。境界は表のとおり（自己資本比率30%は標準、債務償還年数10年は標準）。債務償還年数は、要償還債務がゼロ以下なら償還原資にかかわらず0年、次に償還原資がゼロ以下なら算定不能。
- **諦めたこと**: 業種別の基準。実務では業種ごとに水準が異なるが、10社程度の検証で業種別の基準を置くと恣意性が増すため、共通の基準にした。数値基準は架空であり、実務の水準を示すものではない。READMEにその旨を明記する。

## 2026-09-30 Pythonを3.14に固定

- **決定**: `.python-version`・`requires-python`・ruff の `target-version`・pyright の `pythonVersion` を、すべて3.14にそろえた。
- **理由**: `requires-python = ">=3.12"` だけだと、uv が最新の3.14を選んで仮想環境を作っていた。ruff と pyright の対象は3.12だったので、実行する版と検査する版が食い違っていた。最初は3.12に固定したが、新規のアプリで古い版に合わせる理由がないため3.14にそろえ直した。
- **注意**: 依存ライブラリが3.14に未対応の場合は、その時点で個別に判断する（今のところ問題なし）。

## 2026-09-30 LLMバックエンドの抽象（`llm/`）

- **決定**: 呼び出しは `LLMBackend`（Protocol）に統一し、`complete(LLMRequest) -> LLMResponse` を非同期で提供する。モデルは呼び出し側が `fast / standard / strong` の3段階で指定し、実モデル名はバックエンドが決める。応答キャッシュは `CachedBackend` としてバックエンドを包む。
- **理由**: Claude Pro の利用枠に制約があるため、ローカルLLMとClaudeを差し替えられることが前提になる。段階で指定すれば、エージェントのコードを変えずに割当だけ変えられる。キャッシュのキーにバックエンド名とモデル名を含めるので、割当を変えたときに古い応答を使い回さない。
- **仕様**: 温度が0より大きい呼び出しも、最初に得た応答を再現する（再現性を優先）。バックエンド固有の失敗は `LLMBackendError` にそろえる。
- **キャッシュしないもの**: 失敗した呼び出し、`max_tokens` で途中で切れた応答（`truncated`）、空の応答。保存すると、以後の同じ呼び出しが不完全な応答を返し続け、評価の数値を静かに歪めるため。壊れたキャッシュ（JSON・UTF-8とも）は読み飛ばして上書きする。キャッシュの読み書きに失敗しても、成功したLLM呼び出しの結果は捨てない。
- **未実装**: `claude_code`（Agent SDK）と `anthropic_api`。前者はProのログインで動くか、規約上問題ないかを確認してから実装する。選ぶと `NotImplementedError` になる。
- **Ollama特有の落とし穴への対処**（コードレビューでの指摘）:
  - `num_ctx` を明示する（既定 16384）。Ollama の既定は短く、超えた分のプロンプトは黙って切り捨てられ、もっともらしい答えが返るため。有報のような長い入力では致命的。さらに、応答の `prompt_eval_count` が `num_ctx` に達したら切り捨ての疑いとしてエラーにする。
  - `think` を設定で切り替える（既定はオフ）。Qwen3 の思考トークンは `num_predict` を消費するので、`max_tokens` を思考で使い切って本文が空になることがある。
- **キャッシュのキー**: バックエンド名・モデル名に加え、出力に影響する設定（`num_ctx`, `think`）を `cache_salt` としてキーに混ぜる。混ぜないと、設定を変えても古い応答が返り続ける。
- **切り捨て検知の限界**: `prompt_eval_count >= num_ctx` の判定は補助にすぎない。Ollama がプロンプトのキャッシュを再利用すると値が小さく出て見逃す。確実に防ぐには、エージェント側でチャンクを数えて入力量を制御する（W2以降の課題）。
- **未検証**: 上記を含め、Ollama の実機との接続。Ollama は未導入で、現状のテストはHTTPをモックしている。`think` パラメータの受理、`done_reason` の値、`prompt_eval_count` が切り捨て時に `num_ctx` になる挙動は、Ollama を導入して確かめる。

## 2026-09-30 PostgreSQL（pgvector + pg_bigm）

- **決定**: `pgvector/pgvector:pg17` にpg_bigm（v1.2-20250903）をソースからビルドして足したイメージを、Docker Composeで動かす。日本語の全文検索は pg_bigm の2-gram（`gin_bigm_ops`）、ベクトル検索は pgvector。
- **理由**: PostgreSQL標準の全文検索（tsvector）は日本語の分かち書きができない。pg_bigmは形態素解析器が不要で、`LIKE` の部分一致がそのまま索引に乗る。RDSなどのマネージドでも使える。
- **検証**: 日本語3行のテーブルで、ベクトルの近傍検索、`likequery('原材料価格')` の部分一致、実行計画で `Bitmap Index Scan`（bigm索引）が使われることを確認した。
- **諦めたこと**: BM25。pg_bigmは2-gramの一致度で順位付けするため、BM25とは順位が異なる。W2でRecall@kを測り、足りなければ検索側でBM25相当のスコアを計算し直す。
- **注意**: ホスト側のポートは5433にした（手元のPostgreSQL 17が5432を使う可能性があるため）。拡張の作成は初回起動時だけ走るので、SQLを変えたら `docker compose down -v` でボリュームを消す。

## 2026-09-30 開発ツールと品質ゲート

- **決定**: uv / ruff / pyright(strict) / pytest / pre-commit を使い、同じ検査を Claude Code の hook・pre-commit・GitHub Actions の3箇所で回す。
- **理由**: Claude が書いたコードにも自分が書いたコードにも同じ基準をかけるため。規約を「お願い」ではなく強制にする。
- **諦めたこと**: mypy との併用。pyright の strict に一本化した（設定が少なく、速い）。
- **トレードオフ**: `agents/`, `llm/`, `api/` などの汎用的な名前をルート直下のパッケージにした（PLAN.md の構成どおり）。配布はしないアプリなので許容するが、外部ライブラリと名前が衝突したら `creditmemo/` 配下に移す。
