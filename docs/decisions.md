# 設計判断ログ

何を選び、何を諦めたかを、その時点で書き溜める。新しいものを上に追記する。

## 2026-09-30 検索（埋め込み・全文・融合）と L2 評価

- **決定**: 検索は「語句側（BM25 文字2-gram）＋ベクトル側（埋め込み）を順位で融合（RRF）」にする。L2 評価（質問に対して、根拠のある本文を上位で取れているか）の結果で選んだ。
- **埋め込みモデル**: 回線が遅い（約1.5MB/s）ので大きさで絞り、`multilingual-e5-small`（384次元、上限512トークン）と `ruri-v3-30m`（256次元、上限8192トークン）の2つで比べた。接頭辞はモデルカードで確認した値で、モデルの仕様としてコードに固定した（クエリ／文書の付け忘れは精度を落とす）: e5 は `query: ` / `passage: `、ruri は `検索クエリ: ` / `検索文書: `。
- **チャンクの最大文字数は600**: 検索の点数ではなく、**入力上限の超過数**で決めた（評価に合わせて調整しないため）。600文字で ruri は超過0件、e5 は文書あたり10〜27件（約4〜10%）が512トークンを超える。超えたチャンクはモデルが黙って切り捨てるので、取り込み時に `over_limit` で数えて記録する。
- **取り込み**（`retrieval/ingest.py`）: 文書の情報とチャンクが変わっていなければやり直さない（トークンの数え直しもしない）。変わっていれば古いチャンクと全モデルの埋め込みを消して入れ直す。**渡していないモデルの埋め込みが消えてしまう場合は、消す前にエラーにする**（コードレビューでの指摘。`--models` で一部のモデルだけ指定した再取り込みで、他のモデルの検索が黙って壊れるため）。ベクトルの次元が宣言と違えば保存しない。
- **全文検索の基準線は、pg_bigm の類似度ではなく BM25 にした**: pg_bigm の `bigm_similarity` は質問文全体を1つの文字列として比べるため、長い質問では共通部分の割合が小さくなり、Recall@5 は 0.2 前後にとどまった。融合の相手としても足を引っ張った（pg_bigm との融合は、ベクトルだけより悪い場合があった）。文字2-gram に分けて BM25（k1=1.5、b=0.75。**調整していない**）で採点すると、少ない箇所にしか出ない2文字ほど重くなり、語句の一致が効く。IDF は全文書で計算し、質問の会社への絞り込みは候補の絞り込みだけに使う。pg_bigm の方式は比較のために残した。
- **L2 の結果**（Recall@5。開発用50問 / 保留データ50問。詳細は `evals/reports/l2_retrieval.md`）:

  | 方式 | 開発用 | 保留データ |
  | --- | --- | --- |
  | 全文（pg_bigm） | 0.18 | 0.20 |
  | 全文（BM25） | 0.84 | 0.92 |
  | ベクトル e5-small | 0.90 | 0.76 |
  | ベクトル ruri-v3-30m | 0.86 | 0.80 |
  | 融合 BM25 + e5-small | 0.94 | 0.94 |
  | 融合 BM25 + ruri-v3-30m | 0.96 | 0.94 |

  **融合は両方のデータで最上位**。ベクトル単独の順位は入れ替わる（開発用では e5、保留データでは ruri が上）ので、どちらのモデルが良いかは決めきれない。MRR は ruri との融合が両方で最も高い（0.855 / 0.864。e5 との融合は 0.811 / 0.814）ので、**既定は BM25 + ruri-v3-30m**（差は小さく、確定ではない）。`Retriever.search` の既定のモードも `hybrid_bm25` にしてある（コードレビューでの指摘。以前は評価で最も悪かった pg_bigm との融合が既定だった）。BM25 の索引は全文書のチャンクから作り、複数の Retriever で共有する。
- **設問の作り方と限界**（`evals/datasets/l2_questions.json`）:
  - 10社×5問の開発用と、別の10社×5問の保留データ。各問は、本文の根拠（ページと引用）を先に選び、そこから質問を Claude が書いた。**人が確認した範囲は、まだ無い**（質問と根拠の対応を人が確かめる作業が残っている）。
  - **質問が根拠の言葉に近い可能性がある**: 根拠から質問を書いているので、語句が重なりやすく、語句の一致に頼る方式（BM25）に有利に働きうる。言い換えの多い実際の質問では、ベクトル側の寄与が大きくなるかもしれない。
  - 分類は「リスク・配当・方針・事業・研究開発・人材」で、リスクに偏り（100問中43問）、人材と研究開発は1問ずつ。分類ごとの件数は1〜25件と小さい。**差が数ポイントの比較は、標本の揺れの範囲**。
  - 正解の判定は「同じ文書で、根拠のページを含み、引用がチャンクの本文に入っている」。チャンクの境界で根拠が隣に分かれると外れになるため、**ページ単位の Recall** も併記した（近い外れの多さを見る）。
  - BM25 を作ったのは、開発用・保留データの両方で pg_bigm の結果を見た後。保留データは「設定を決めるときには使っていない」とは言えなくなった（BM25 の構成は結果を見て選んだが、パラメータは調整していない）。次に新しい設問を足すときは、新しい会社で作る。
- **DB の書き込みが消えるバグ**: 接続を閉じるときに、未コミットの取り込みが巻き戻され、評価が全て0になった（psycopg のトランザクションの既定）。接続を autocommit にし、別の接続から読める回帰テストを足した。書き込み（`upsert_document`、`add_embeddings`）は `with conn.transaction()` で明示的にまとめ、途中で失敗したら巻き戻る。
- **未着手**: リランク（効果を測ってから）、3方式（pg_bigm も含む）の融合、より言い換えの多い設問。

## 2026-09-30 本文のチャンク分け（`retrieval/chunker.py`）

- **決定**: PDF の本文を、見出しの階層とページ範囲つきのチャンクに分ける。検索の単位であり、メモの出典（何ページのどの節か）の単位でもある。
- **規則**（実データの書式で確かめた）:
  - 各ページの先頭3行（`EDINET提出書類`、会社名(E…)、`有価証券報告書`）と末尾のページ番号（`63/137`）は本文に含めない。
  - 見出しは4階層: `第一部 【…】`、`第2 【…】`、`1 【…】`（`1【連結貸借対照表】` のようにスペースが無い書き方も）、`(1) …`。階層はページをまたいで引き継ぐ。見出しの行は本文に入れず、階層としてチャンクに持たせる。チャンクは見出しをまたがない。
  - **行の途中では切らない**（表の行を壊さないため）。1行が最大文字数（既定600）より長いときだけ、句点で区切って詰め、句点が無ければ文字数で切る。
  - チャンクIDは `<文書ID>:<連番>`。同じ入力なら同じ結果になる。
- **項の見出し `(1) …` の誤検出を防ぐ**: 表の行や本文の文にも `(1)` で始まる行がある。数値が2つ以上並ぶ行、日付（`2024年`）を含む行、句点を含む行、`(1)` を除いて41文字以上の行は見出しにしない。日付の行は、実データで誤検出が見つかった（PDF の折り返しで「添」で切れた、書類の一覧の表の行）。
- **実データでの結果**（20社の当期の有報）: 1社あたり212〜403チャンク、平均長は440〜555文字。見出しの無いチャンクは全社で表紙の1つだけ。「事業等のリスク」の節は全社で見つかった（3〜20チャンク）。
- **未確定**: 最大文字数は800から600に変えた（理由は上の「検索（埋め込み・全文・融合）と L2 評価」）。

## 2026-09-30 PDF の基準線（pdfplumber）と L1 評価

- **決定**: PDF の構造化の最初の方式を、モデルを使わない pdfplumber ＋規則にした（`ingest/pdf_baseline.py`）。Docling などと比べる物差し（基準線）にするため。L1 は、財務諸表にそのまま載っている 11 項目（総資産・純資産・流動資産・流動負債・売上高・営業利益・受取利息・受取配当金・支払利息・親会社株主に帰属する当期純利益・減価償却費）を、XBRL の正解データと突き合わせて採点する（`evals/l1.py`）。
- **方式**:
  - 連結貸借対照表・損益計算書・キャッシュ・フロー計算書を**見出しの行**で特定する。同じ項目名は注記や個別財務諸表にも出るので、範囲を限らないと誤る。CF は見出しから最大3ページで、注記の見出しで打ち切る。
  - 項目ごとに載っている書類が決まっている。減価償却費は損益計算書の販管費の内訳にも出るが、正解データは CF の値。
  - 「前期 当期」の2列から、最後の数値を当期として読む。単位（百万円・千円）を円に直す。
  - **注記の印（※1）は小さい文字（本文9.0に対し6.0）で、数値に癒着して取り出される**（`※1423,923` は注記1＋423,923）。桁数では見分けられないので、本文の中央値の8割より小さい文字を除いてから取り出す。
  - 長いラベルは2行に折り返される（数値が2行目の後ろ、または3行目に来る）。数値の無い直前の最大2行を結合したラベルも候補にする。
  - 各値に、読んだページと行を記録する。
  - **損失のラベルは符号を負にそろえる**: 「営業損失」「親会社株主に帰属する当期純損失」のように利益を含まない損失のラベルは、損失額を正の数で印字することがあるが、XBRL では負の値。値を `-abs(値)` にする（△付きで印字されていてもそのまま負）。「営業利益又は営業損失(△)」は印字どおりに読む（コードレビューでの指摘。対象20社には損失の会社がなく、実データでは未確認で、テストは合成データ）。
  - **1列だけの表も読む**: 節の中に「前連結会計年度」の見出しがあれば2列の表とみなし、数値が1つの行は列の対応が分からないので読まない。見出しが無ければ（初回の有報など）1列として読む。継続ページに見出しが無いため、ページではなく節全体で判定する。
  - **CF の範囲は、注記の見出しのページまで含めて、見出し以降を切り捨てる**: CF と注記が同じページにあると、範囲が空になり減価償却費が「範囲なし」になる（コードレビューでの指摘）。注記の同名の行（減価償却費など）を拾わないよう、抽出のときに見出しより前だけを読む。
  - **2列かどうかは、列の見出しの行（「前連結会計年度 当連結会計年度」）だけで判定する**: 注記の文中の「前連結会計年度」を根拠にすると、1列の表の行を読み飛ばす。
  - **本文のキャッシュには版番号をつける**（`TEXT_EXTRACTION_VERSION`）: 取り出し方を変えても古い本文で採点し続けないため。版が違う・壊れている・ページが0件のキャッシュは使わず、0件の結果は保存しない。
- **結果**（正答＝一致または両方なし。レポートは `evals/reports/`。数値は載せない）:
  - 開発用 10 社: 初回 107/110。失敗3件は書式の違い（ラベルの折り返し2件、受取利息が合算の行1件）で、規則で解決して 110/110。
  - **保留データ（規則の作成時に PDF を見ていない無作為の10社）: 規則を変えずに 110/110。** 開発用が過剰適合ではなかったことの確認。
- **この数字の解釈と限界**:
  - EDINET の PDF は、EDINET が提出書類から生成する**統一書式**で、全社が同じ体裁。基準線が強いのは、この統一書式のため。**この 11 項目の L1 は飽和しており、Docling などを同じ L1 で比べても差はほとんど出ない。**
  - 標本は小さい: 保留データは10社×11項目。誤りが0件でも、真の誤り率の上限は約3%（rule of three）。
  - 対象は J-GAAP・連結・中堅企業。保留データは全社3月決算（12月決算は開発用の1社のみ）。IFRS、スキャン画像の PDF、決算説明資料のような EDINET 生成でない文書は未評価。
  - 合成項目（売上債権・棚卸資産・仕入債務・有利子負債）、注記の表、図・グラフは未評価。
- **設計上の含意**: EDINET の提出書類には、数値の正である XBRL がある。財務数値は XBRL から取る（機械可読で、正確）のが実務的で、PDF は次の用途に使う。
  1. 数値の**出典**（ページと行）を示す。基準線が各値のページと行を記録しているのはこのため（メモの出典スパンに使う）。
  2. XBRL に無い**本文と表**（事業等のリスク、大口取引先への依存、セグメント情報、ガバナンス）を読む。
  PDF の構造化方式の比較（Docling・YomiToku・VLM）は、財務数値ではなく、この2つ目の用途で意味を持つ。

## 2026-09-30 XBRL からの正解データ（`ingest/xbrl_facts.py`、`evals/ground_truth.py`）

- **決定**: EDINET の財務データ CSV から規程の入力項目を読み、L1 評価の正解データにする。J-GAAP の連結のみ対象で、IFRS の書類は黙って空にせず `UnsupportedAccountingStandard` で失敗させる。出力は `data/ground_truth/ground_truth.json`（EDINET 由来のデータなので gitignore。利用規約の確認までは公開しない）。
- **読む値**: 連結の、当期（または前期）の、軸のないコンテキストだけ。前期は当期の書類の前期の列から読む。前期の書類の当期の列と食い違えば、訂正再表示の疑いとして記録する。
- **合成項目の規則**（対象10社の実データの項目名で確かめた）:
  - 売上債権: 「受取手形、売掛金及び契約資産」の行があればそれ、無ければ「受取手形及び売掛金」の行に契約資産を足し、それも無ければ受取手形・売掛金・契約資産の内訳を足す。**電子記録債権は別の行なので、いずれの場合も足す。** 合計の行と内訳の行が同時に出るため、合計の行があれば内訳は足さない（二重に数えない。能美防災で 5,334 + 36,039 + 20,986 ≒ 合計の行 62,360 を確認した）。
  - 棚卸資産: 「棚卸資産」の行があればそれ、無ければ商品及び製品・仕掛品・原材料及び貯蔵品の内訳に、**不動産の販売用不動産・仕掛販売用不動産と、建設の未成工事支出金**を足す。
  - 仕入債務: 「支払手形及び買掛金」（建設業は独自の項目）に、営業の電子記録債務を足す。営業外の電子記録債務は含めない。
  - 受取配当金: 保険配当金は含めない。受取利息と受取配当金が合算の行しかない会社は、合算を受取利息として扱う（インタレスト・カバレッジの分子は合計なので足りる）。
  - 有利子負債: 「－」（行はあるが金額なし）は0として扱い、**行そのものが無い場合（None）と区別する。** 能美防災は短期借入金の行が「－」で、借入が無いことが分かる。
- **出所を記録する**: 各項目が、どの XBRL 項目から得た値かを `provenance` に残す。合成項目の規則が正しいかを、後から確かめられるようにするため。
- **「－」は優先順位で後回しにする**: 先頭の候補が「－」（0）でも、値のある後ろの候補や内訳があればそちらを使う（コードレビューでの指摘）。候補がすべて「－」なら0。合計の行が「－」の場合も、値のある内訳を足す。
- **連結の行が1つも無い書類は失敗させる**: 個別のみ、または形式を読めない書類で、すべて `None` の結果を黙って返さないため（`NoConsolidatedStatements`）。IFRS は別の例外（`UnsupportedAccountingStandard`）。
- **数値でない行を読まない**: `Decimal` は "NaN" や "Infinity" を受け付けるので、有限の数だけを金額として読む。
- **実データで未観測の項目名**: 固定負債の新株予約権付社債（`BondsWithSubscriptionRightsToShares`）と、コマーシャル・ペーパー（`CommercialPapersLiabilities`）は、対象10社に出てこず、実データで確かめていない（テストは合成データ）。名前が違えば、単に一致せず None のままになる。対象企業を増やしたときに確認する。
- **実データでの結果**:
  - 前期の列と前期の書類の当期の列は、10社とも一致した（訂正再表示なし）。ただし、片方の書類でだけ「－」（0）と載り、もう片方には行が無い、という表示の違いがあった（西武HD・積水化成品の1年内償還予定の社債）。0と「行なし」は同じとみなして、訂正再表示と区別する。
  - 選定時の概算（`companies.json`）と、正解データから計算した3指標は、10社とも一致した。
  - 取れなかった項目: エスコンの仕入債務（不動産会社にその行が無い）。メイテックは有利子負債・支払利息・仕入債務・受取配当金が無い。この2社は債務償還年数が算定不能になる（メイテックはインタレスト・カバレッジも）。**「行が無い = 0」なのか「抽出漏れ」なのかは区別できない**（前述の未解決事項の実例）。メモでは「確認が必要な事項」に回す。
  - **債務償還年数は、この規程の定義（有利子負債 − 正常運転資金）だと判別力が低い。** 10社中5社が 0.0 年（正常運転資金が有利子負債を上回る）で、水準がつくのは西武HD（6.5年）と高砂（0.3年）などにとどまる。欠陥ではなく規程の定義の性質。メモでは0年の会社に「無借金」と書かず、「正常運転資金が有利子負債を上回るため」と根拠を書く。
  - **西武HDの営業収益は 9,011億円 → 5,133億円（−43%）、営業利益は 2,927億円 → 455億円。** 書類の中で辻褄は合っている（前期の列と前期の書類が一致）。第11条に該当するが、**原因はこの数値だけでは分からない**ので、メモには理由を推測で書かず、確認が必要な事項にする（規程 第18条）。積水化成品（−16.9%）は、投資活動に「連結範囲の変更を伴う子会社株式の売却による支出」があり、事業の切り離しと整合する。アイネス（−9.7%）は第11条の境界のすぐ内側。

## 2026-09-30 EDINET クライアント（`ingest/edinet.py`）

- **決定**: 書類の取得を、冪等・原子的・キー非表示の小さなクライアントにした。種別は PDF（`type=2`）、XBRL の zip（`type=1`）、財務データの CSV の zip（`type=5`）。保存先は `data/edinet/<docID>/`（gitignore）。
- **キーを出さない**: EDINET はキーを URL のクエリで渡すため、httpx が INFO で出すリクエスト URL にキーが含まれる（初回の確認スクリプトで実際に漏れた）。モジュールを import した時点で httpx / httpcore のログを WARNING 以上にし、例外のメッセージには URL を入れず型名だけを残す。ログとエラーにキーが出ないことをテストで固定した。
- **壊れたファイルを残さない**: EDINET は失敗時にも HTTP 200 でエラーの JSON を返すことがある。先頭のバイト列（PDF は `%PDF`、zip は `PK`）を確認し、一時ファイル経由で置き換える。
- **リトライ**: 5xx・429・接続エラーは、初回を含め最大3回（待ち時間を増やす）。それ以外の 4xx は直らないので即失敗にする。リクエストの間には 0.5 秒待つ。
- **再取得しない**: 保存済みで空でないファイルは取得しない。回線が遅い（約 1.5MB/s）ので、中断後の再実行で続きから進めるようにするため。
- **一括取得は続行する**: 1件失敗しても残りを取得し、失敗は結果に含めて返す。

## 2026-09-30 財務比率の計算（`finance/ratios.py`）

- **決定**: 規程の附則・第8条・第10条・第11条を、言語モデルを介さず純粋な関数として実装した。テストは規程の条文をそのまま仕様にして、境界値（30%ちょうど、10年ちょうど など）まで先に書いた。
- **Decimal を使う**: 「30%ちょうど」が標準か留意かを分ける規程なので、浮動小数点の誤差で判定が変わらないようにした。
- **計算根拠を併記する**: 各指標に、算式と入力値を書いた文字列（`basis`）を持たせた（規程 第7条第2項）。メモの数値は、これを転記する。
- **入力の欠落は0にしない**: XBRL に項目が無い場合は `None` とし、その指標を「入力なし」で算定不能にする。無い項目を0として計算すると、もっともらしい誤った数値が出るため。例外は次の2つで、どちらも「無い会社では項目自体が出ない」ため0として扱う。
  - 有利子負債の内訳（借入金・社債・リース債務など）のうち、一部が未計上のもの。
  - 受取利息・受取配当金（インタレスト・カバレッジ・レシオの分子）。
  - **有利子負債の内訳がすべて未計上の場合は0にせず、債務償還年数を算定不能にする**（水準は付けない）。すべて0とみなすと、抽出に失敗した会社が「0年・標準」という最良の評価になるため（コードレビューでの指摘）。本当に借入のない会社は、取り込み側が0を明示する。
- **規程があいまいだった点の扱い**:
  - 債務償還年数の算定不能を要精査水準とする第8条第2項ただし書きは、「償還原資がゼロ以下」の場合だけに適用した。**入力が無くて算定できない場合は水準を付けない**（データの欠落を、財務の悪化と同じ扱いにしないため）。
  - 要償還債務がゼロ以下と償還原資がゼロ以下が同時に成り立つ場合は、附則第3条の順序どおり、要償還債務を先に判定して0年とする。
  - 売上高成長率には水準の区分がなく、第11条の該当・非該当だけがある。
- **未解決（W1 の実データで判断する）**: 支払利息の項目が XBRL に無いとき、それが「支払利息なし（ゼロ）」なのか「別の科目名で計上されていて取れていない」のかを、いまは区別できない。現状は「支払利息なし」と断定せず、「支払利息の項目がない（…確認が必要）」という理由で算定不能にして、メモの「確認が必要な事項」に回す。実データで、営業外費用の内訳の出方を見て決める。
- **表示は、判定が変わらない最小の桁数で出す**: 通常は小数1桁。ただし丸めると判定が変わる値（自己資本比率 29.96% を「30.0%」と表示すると、留意なのに標準と読める）は、判定が保たれるまで桁を増やす。第11条の売上高の減少（−9.96% を「−10.0%」とすると該当と読める）も同様（コードレビューでの指摘）。

## 2026-09-30 LLMバックエンドの抽象（`llm/`）

- **決定**: 呼び出しは `LLMBackend`（Protocol）に統一し、`complete(LLMRequest) -> LLMResponse` を非同期で提供する。モデルは呼び出し側が `fast / standard / strong` の3段階で指定し、実モデル名はバックエンドが決める。応答キャッシュは `CachedBackend` としてバックエンドを包む。
- **理由**: Claude Pro の利用枠に制約があるため、ローカルLLMとClaudeを差し替えられることが前提になる。段階で指定すれば、エージェントのコードを変えずに割当だけ変えられる。キャッシュのキーにバックエンド名とモデル名を含めるので、割当を変えたときに古い応答を使い回さない。
- **仕様**: 温度が0より大きい呼び出しも、最初に得た応答を再現する（再現性を優先）。バックエンド固有の失敗は `LLMBackendError` にそろえる。
- **キャッシュしないもの**: 失敗した呼び出し、`max_tokens` で途中で切れた応答（`truncated`）、空の応答。保存すると、以後の同じ呼び出しが不完全な応答を返し続け、評価の数値を静かに歪めるため。壊れたキャッシュ（JSON・UTF-8とも）は読み飛ばして上書きする。キャッシュの読み書きに失敗しても、成功したLLM呼び出しの結果は捨てない。
- **未実装**: `anthropic_api`。選ぶと `NotImplementedError` になる。`claude_code` は下記の別項目で実装した。
- **Ollama特有の落とし穴への対処**（コードレビューでの指摘）:
  - `num_ctx` を明示する（既定 16384）。Ollama の既定は 4096 と短く（サーバーのログで確認）、超えた分のプロンプトは黙って切り捨てられ、もっともらしい答えが返るため。有報のような長い入力では致命的。
  - `think` を設定で切り替える（既定はオフ）。Qwen3 の思考トークンは `num_predict` を消費するので、`max_tokens` を思考で使い切って本文が空になることがある。
- **キャッシュのキー**: バックエンド名・モデル名に加え、出力に影響する設定（`num_ctx`, `think`）を `cache_salt` としてキーに混ぜる。混ぜないと、設定を変えても古い応答が返り続ける。
- **入力が収まるかは、送る前に見積もって止める**（実機で分かったこと）: Ollama は `num_ctx` に収まらない入力を、警告ログ（`truncating input prompt`）だけで黙って切り詰めて実行し、応答の `prompt_eval_count` も切り詰め後の値を返す。`num_ctx=512` に約 4,400 トークンの入力を送ると、258 トークンとして「成功」した。応答の数値では確実に検知できないため、`prompt_eval_count` による判定は外し、送信前に「入力の文字数 × 1.25 + 定型分（全体で 64 + メッセージ 1 通ごとに 16）+ `max_tokens` が `num_ctx` に収まるか」を確かめる方式にした。
  - 1.25 は、Qwen3 のトークナイザで実測した 1 文字あたりのトークン数（日本語の散文 0.69、数値の表 0.89、有報風の文章 0.95、英数字 0.56）の最大に約3割の余裕を足した値。珍しい漢字や記号（▲△、絵文字）は 1 文字が複数トークンになりうるため、実測の上限そのもの（1.0）では足りないと、レビューで指摘された。英数字が多い入力は過大評価になるが、安全側。
  - 既定（`num_ctx=16384`、`max_tokens=2048`）では、入力は約 11,000 文字まで。それより長い入力は、チャンクに分けるか `LOCAL_NUM_CTX` を上げる。
  - 限界: 実測は 4 種類のサンプルだけ。見積もりを超える入力が来たときに拾う仕組みは他にない。W2 でチャンクを作るときに、実際の有報の文章で比を測り直す。
- **実機で確認できたこと**（qwen3:8b、Ollama 0.35.0）: `think` の指定は受理され、`<think>` は本文に混じらない。`max_tokens` で切れると `done_reason` が `length` になり、`truncated=True` が立つ。
- **8B の精度**: 「自己資本比率とは」に対し「自己資本が**純資産**の何％を占めるか」と誤って答えた（正しくは総資産に対する割合）。金融の基礎知識で誤りが出るため、根拠のない出力を前提にする用途（起草・検証）には使えない。開発中の反復（配線・形式の確認）に限り、内容の品質はClaudeで評価する。

## 2026-09-30 PostgreSQL（pgvector + pg_bigm）

- **決定**: `pgvector/pgvector:pg17` にpg_bigm（v1.2-20250903）をソースからビルドして足したイメージを、Docker Composeで動かす。日本語の全文検索は pg_bigm の2-gram（`gin_bigm_ops`）、ベクトル検索は pgvector。
- **理由**: PostgreSQL標準の全文検索（tsvector）は日本語の分かち書きができない。pg_bigmは形態素解析器が不要で、`LIKE` の部分一致がそのまま索引に乗る。RDSなどのマネージドでも使える。
- **検証**: 日本語3行のテーブルで、ベクトルの近傍検索、`likequery('原材料価格')` の部分一致、実行計画で `Bitmap Index Scan`（bigm索引）が使われることを確認した。
- **諦めたこと**: BM25。pg_bigmは2-gramの一致度で順位付けするため、BM25とは順位が異なる。W2でRecall@kを測り、足りなければ検索側でBM25相当のスコアを計算し直す。
- **注意**: ホスト側のポートは5433にした（手元のPostgreSQL 17が5432を使う可能性があるため）。拡張の作成は初回起動時だけ走るので、SQLを変えたら `docker compose down -v` でボリュームを消す。
